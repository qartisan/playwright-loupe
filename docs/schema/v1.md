# Loupe JSON report — schema v1

Loupe writes `report.json` next to `index.html` in its output folder. This JSON is Loupe's **public contract**: the HTML renderer reads it, and so can any other tool.

- **Source of truth:** TypeScript types in [`src/schema/v1.ts`](../../src/schema/v1.ts), exported from the package: `import type { LoupeReport } from '@qartisan/playwright-loupe'`.
- **JSON Schema:** [`report-v1.schema.json`](report-v1.schema.json) (draft 2020-12). Every report produced by the test suite is validated against it.
- **Attachments** live in the `data/` folder next to `report.json` and are referenced by relative path.

## Conventions

- Every field is always present. A missing value is an explicit `null`, never an absent key. Objects never carry extra keys.
- Durations are integer milliseconds (`…Ms`), never negative.
- Dates are ISO 8601 strings in UTC (`2026-10-12T14:40:49.422Z`).
- File paths are **relative to the Playwright root dir, with POSIX separators** (see [Paths](#paths)).

## Versioning policy

- `schemaVersion` is an integer. This document describes version `1`.
- **Any change to the shape** — adding, removing or renaming a field, changing a type, adding a value to an enumeration — produces a new `schemaVersion`, with its own types file, JSON Schema and documentation.
- Changes that keep the shape (better category rules, a new CI provider detected, a new `scopeReasons` value, more precise normalization) do not change the version. They are listed in the release notes, because some of them change computed values such as signatures.
- `scopeReasons` is an open list of strings on purpose: new reasons can appear without a version bump. Consumers must accept unknown values.

### Pre-publication amendments

Until the first npm publication, v1 can still be **amended in place**: no published report or consumer depends on it yet. After the first publication, any shape change requires a new `schemaVersion`.

| Amendment | Change |
| --- | --- |
| Run errors | `Run.errors` ([`RunError[]`](#runerror)): errors not attached to a test. |
| Expected dimension values | `DimensionDefinition.values` (`string[] \| null`). Configured dimensions are always listed in `dimensions`, even when no test uses them. |

## Identity

### Test id

```
id = first 16 hex chars of sha256(project + "\0" + file + "\0" + [...suitePath, title].join("\0"))
```

- `project` is the project name (`""` for an unnamed project), `file` the [relative path](#paths), `suitePath` the `describe()` titles and `title` the test title.
- NUL (`\0`) cannot appear in titles, so different title paths never join into the same string.
- The id is stable across runs, machines and operating systems, and between a normal run and a sharded run merged with `merge-reports`. It changes when the test, one of its `describe()` blocks, its file or its project is renamed or moved.
- By design, the same test in two projects has two ids, and the same title in two files has two ids.
- With `--repeat-each`, Playwright runs the same test several times as separate tests: they share the same `id` and differ by `repeatEachIndex`. The pair (`id`, `repeatEachIndex`) is unique within a report.

### Paths

All file paths (`TestCase.file`, `Project.testDir`, error and step `location.file`) are relative to Playwright's **root dir** (`config.rootDir`, i.e. the top-level `testDir`, which defaults to the directory of the config file) and use `/` separators. A file outside the root dir starts with `../`; the root dir itself is `.`.

Why the root dir rather than the config file's directory: blob reports store paths relative to the root dir, and `merge-reports` rebases them on the root dir of the merge config. Using the same base keeps paths and ids identical between a normal run and a merged one.

> **merge-reports:** the merge config's root dir must match the one used by the shards. Put the merge config next to the original config with the same `testDir`, or set `testDir` explicitly (see [`fixtures/merge.config.ts`](../../fixtures/merge.config.ts)).

Stack traces (`LoupeError.stack`) are kept as Playwright reports them, with absolute paths.

### Git and CI detection

Loupe never runs `git` itself. Each field takes the first value found:

1. Playwright's own metadata: `metadata.gitCommit` (captured when [`captureGitInfo.commit`](https://playwright.dev/docs/api/class-testconfig#test-config-capture-git-info) is enabled, by default on CI, from Playwright 1.51), then `metadata.ci`. A branch reported as `HEAD` (detached checkout) is ignored.
2. CI environment variables:

| | commit | branch | remote |
| --- | --- | --- | --- |
| GitHub Actions | `GITHUB_SHA` | `GITHUB_HEAD_REF`, else `GITHUB_REF_NAME` when `GITHUB_REF_TYPE` is `branch` | `GITHUB_SERVER_URL`/`GITHUB_REPOSITORY` |
| GitLab CI | `CI_COMMIT_SHA` | `CI_COMMIT_BRANCH`, else `CI_MERGE_REQUEST_SOURCE_BRANCH_NAME` | `CI_PROJECT_URL` |
| Azure Pipelines | `BUILD_SOURCEVERSION` | `BUILD_SOURCEBRANCHNAME` | `BUILD_REPOSITORY_URI` |
| CircleCI | `CIRCLE_SHA1` | `CIRCLE_BRANCH` | `CIRCLE_REPOSITORY_URL` |
| Jenkins | `GIT_COMMIT` | `GIT_BRANCH` | `GIT_URL` |
| Bitbucket | `BITBUCKET_COMMIT` | `BITBUCKET_BRANCH` | `BITBUCKET_GIT_HTTP_ORIGIN` |
| Buildkite | `BUILDKITE_COMMIT` | `BUILDKITE_BRANCH` | `BUILDKITE_REPO` |

Locally, without `captureGitInfo`, all three are `null`.

### Run scope

A run is `partial` when it deliberately ran only part of the suite, typically from the CLI or an IDE while debugging. Phase 2 excludes partial runs from statistics by default.

| Reason | Detected from |
| --- | --- |
| `env` | `LOUPE_RUN_SCOPE=partial` (listed first, followed by any detected reason). |
| `file-filter` | Positional arguments of `playwright test` (files, `file:line`). |
| `grep` | `-g` / `--grep` / `--grep-invert` on the command line, or a top-level `grep` / `grepInvert` in the config file. |
| `project-filter` | `--project` leaving out at least one default project (see [Default projects](#default-projects)). A project needed as a dependency or teardown of a selected project does not count as left out, unless `--no-deps` is used: then dependencies and teardowns do not run and count as left out. |
| `last-failed` | `--last-failed`. |
| `only-changed` | `--only-changed`. |
| `test-list` | `--test-list` / `--test-list-invert`. |
| `only` | A `test.only` or `describe.only` in effect. |
| `shard` | A sharded run (`--shard` or `shard` in the config): one shard does not cover the suite. A merged report has no shard. |
| `list` | `--list`: tests are listed, nothing runs. It does not mean a filtered subset: no test has a result, whatever the other reasons say. Other filters on the same command line are reported as well. |

#### Default projects

The reference for a full run is the set of **default projects** as the config defines them, not every configured project. A project with `default: false` only runs when selected with `--project`, so its absence never makes a run partial. A run is `partial` (`project-filter`) when at least one default project, with its transitive dependencies and teardowns, did not run. A non-default project counts only when it is explicitly selected.

With `main` and `setup` as default projects (`main` depends on `setup`) and `nightly` set to `default: false`:

| Command | Projects that run | Scope |
| --- | --- | --- |
| `playwright test` | `setup`, `main` | `full`: `nightly` is not a default project |
| `playwright test --project nightly` | `nightly` | `partial` (`project-filter`): the default projects are missing |
| `playwright test --project main nightly` | `setup`, `main`, `nightly` | `full` |

`default: false` exists from Playwright 1.64; before, every project is a default project. Reporters do not get the flag through the public API: Loupe reads it from Playwright's internal config. When it is not available, a plain `playwright test` (no `--project`) still counts as covering the default projects, since Playwright already left the others out of `config.filteredProjects`, but with `--project` every configured project is the reference.

**Override.** `LOUPE_RUN_SCOPE=full` forces `full` with no reasons; `LOUPE_RUN_SCOPE=partial` forces `partial`. Any other non-empty value stops the run with an explicit error.

**Default.** `full` when nothing indicates otherwise.

**How it works, and its limits.** Playwright does not pass most CLI filters to reporters. What a reporter can see, checked against Playwright 1.52 to 1.64:

- CLI `--grep`, file filters, `--last-failed`, `--only-changed`, `--test-list` and `--list` never reach the resolved config (`config.grep` keeps its default). The only trace is the command line: `config.argv` from Playwright 1.61, `process.argv` before (the reporter runs in the main process, so both are the `playwright test` command line). Loupe parses it with the list of `playwright test` options that take a value.
- `--project` is read from `config.filteredProjects` (Playwright 1.64+). Before, Loupe checks the command line for `--project` and compares the projects present in the run with the config. Under `merge-reports`, `filteredProjects` is empty and `argv` is empty or the merge command line; both are treated as "no filter".
- `--no-deps` is not reflected in the config reporters get (`project.dependencies` and `teardown` are kept): Loupe reads it from the command line, so that dependencies of the selected projects do not count as running. Before 1.64, the projects present in the run already show it.
- `default: false` is read from Playwright's internal config (see [Default projects](#default-projects)). It is not a public API either; `test/scope.integration.test.ts` checks the three cases above on Playwright 1.64 and later.
- `test.only` is read from Playwright's internal `_only` flag on tests and suites. It is not a public API and may change: `test/only.integration.test.ts` runs a fixture with a real `test.only` on every Playwright version of the CI matrix, so a change breaks CI instead of silently reporting `full`.
- A `grep` declared on a **project** is part of that project's definition and does not make the run partial.

Known limits:

- **IDE and UI mode.** The VS Code extension and UI mode run tests through a test server whose command line is not `playwright test`, so their filters are not visible: the run is reported `full`. Set `LOUPE_RUN_SCOPE=partial` in those environments if needed.
- **Programmatic and wrapper launches** with a different command line are not parsed.
- **Merged reports** see the `merge-reports` command line, not the shards' ones: a merged report is `full` unless the blobs came from filtered runs and `LOUPE_RUN_SCOPE` says so.
- `--only-changed` and `-u` take an optional value, like Playwright's own parser: `--only-changed main` treats `main` as the git ref, not as a file filter.
- `--project` takes every following value up to the next option, like Playwright's own parser: in `--project a b.spec.ts`, `b.spec.ts` is a project name (Playwright rejects it), not a file filter. `--project=a` takes one value.

## RunError

An error Playwright reported outside any test, through the reporter's `onError`. A run can have run errors and **zero tests**: it still produces a valid report, and these errors are the only trace of what went wrong. Renderers must show them prominently.

| Field | Type | Description |
| --- | --- | --- |
| `message` | `string` | Error message, ANSI codes stripped. Absolute paths are kept. |
| `stack` | `string \| null` | Stack trace, ANSI codes stripped. |
| `location` | `{ file, line, column } \| null` | Where the error happened, [relative](#paths). See below for load errors. |
| `snippet` | `string \| null` | Source excerpt, ANSI codes stripped. |
| `signature` | `string` | [Error signature](#error-signature), same normalization as test errors. |
| `category` | `string \| null` | [Error category](#error-categories), same rules as test errors. Rules with `on: 'step'` never match a run error. The `merge-reports` tag prefix is ignored ([see below](#merge-reports)). Always set in v1. |
| `project` | `string \| null` | Project of the worker that produced the error, when Playwright gives it; `null` otherwise. |

### What reaches a reporter

Checked against Playwright 1.52 and 1.64:

| Situation | What the reporter receives | `location` | `project` |
| --- | --- | --- | --- |
| A spec file fails to load (missing module, syntax error, error at import time) | One `onError` per file. **Playwright then runs no test at all**, the other files included: `tests` and `projects` are empty. | CommonJS spec files: the failing line. ES module spec files: Playwright reports `<anonymous>:1:1`; Loupe takes the importing file from the message (`Cannot find module '…' imported from <file>`) and the line of the import with the missing specifier. `null` when it cannot be found. | `null` |
| `globalSetup` throws | `onError`; no test runs. | The `throw` in the setup file. | `null` |
| `globalTeardown` throws | `onError` after the tests. | The `throw` in the teardown file. | `null` |
| A worker-scoped fixture fails in teardown | `onError`; the message ends with the tests the worker ran. | The fixture. | Recent Playwright versions pass the worker's project; 1.52 does not (`null`). |
| A worker crashes during a test (`process.exit`, crash) | No run error: the test currently running fails with the crash. | — | — |
| `afterAll` hook throws or the worker exits in it | No run error: attributed to the last test of the worker. | — | — |

Errors that stop Playwright before reporters exist (an invalid `playwright.config.ts`, an invalid Loupe config) produce no report.

### merge-reports

Run errors are stored in blob reports and **survive `merge-reports`**: a blob is written even when a spec file failed to load, and the merged report lists its errors in `run.errors` (covered by `test/load-error.integration.test.ts`). `project` survives the merge too when the shard had it.

When the shard's config has a `tag` option, `merge-reports` (Playwright 1.57 and later) prefixes the message and stack of its run errors with `(<tags>) ` so you can tell which run they come from, e.g. `(@chromium) Error: …`. `message` and `stack` keep the prefix, but the [signature](#error-signature) and the [category rules](#error-categories) ignore it: the same error has the same signature and category merged or not, and a rule anchored with `^` matches it either way (covered by `test/load-error.integration.test.ts`). The prefix is removed as described in [Error signature](#error-signature), step 2, from the message and from the stack before rules are tested.

The legacy `PWTEST_BOT_NAME` variable adds a `(<name>) ` prefix the same way, inside the tag prefix. Its name is free text that cannot be told apart from the error message, so it is **not** stripped: it changes the signature and is seen by category rules.

Locations are relativized against the merge config's root dir, like test locations. The ES module load-error location is recovered only when the spec file exists at the same path on the machine running `merge-reports`.

`{ text: string, truncated: boolean }`. The chunks written by the attempt are joined, ANSI codes are stripped, and only the **first 32,768 characters** (UTF-16 code units, never splitting a character) are kept. `truncated` is `true` when something was cut.

## Attachment

| Field | Type | Description |
| --- | --- | --- |
| `name` | `string` | Attachment name. |
| `contentType` | `string` | MIME type as declared. |
| `kind` | `'screenshot' \| 'video' \| 'trace' \| 'text' \| 'other'` | See below. |
| `path` | `string \| null` | File in the report folder, relative to it: `data/<testId>/<attemptIndex>/<file>`. `null` when the body is inline or the source file no longer existed. |
| `body` | `string \| null` | Inline body for small text attachments, `null` otherwise. |
| `comparison` | `{ group, role } \| null` | Set for snapshot comparison images. |

**Storage.**

- File attachments (`path`) are copied into `data/<testId>/<attemptIndex>/`, keeping the source file name. With `--repeat-each`, iterations after the first use `data/<testId>-r<repeatEachIndex>/`.
- Body attachments are inlined when their content type is text (`text/*`, JSON, XML) and the body is at most **4,096 bytes** (UTF-8). Other bodies are written to a file named after the attachment, with an extension from the content type.
- Names are made safe (one path segment, no leading dot, at most 100 characters). A name already used in the same folder gets a `-1`, `-2`, ... suffix.
- Videos and traces are copied as is. The `data/` folder is emptied before each report is written.

**Kind.** `image/*` → `screenshot`; `video/*` → `video`; name `trace`, or `application/zip` with "trace" in the name → `trace`; text types → `text`; anything else → `other`.

**Comparison.** `toHaveScreenshot()` and `toMatchSnapshot()` on images attach `<name>-expected.<ext>`, `<name>-actual.<ext>` and `<name>-diff.<ext>`. For image attachments named that way, `comparison.role` is `expected`, `actual` or `diff`, and `comparison.group` is `<name>.<ext>`, shared by the three images of one comparison.

## Error signature

The signature groups identical failures across tests, retries and runs. It depends only on the error message: not on the test, the stack, the location or the code frame (`snippet`), which are separate fields.

```
signature = first 12 hex chars of sha256(normalize(message))
```

Normalization, in this order:

1. Strip ANSI codes.
2. Run errors only: remove the `(<tags>) ` prefix that `merge-reports` adds for a shard config with a `tag` ([see above](#merge-reports)). It is removed once, only at the very start of the message, and only in that shape: `(`, then `@`, then any characters except parentheses and line breaks, then `) `. Config tags always start with `@`, so a message such as `(intermediate value) is not a function` is left as is. Test and step errors never get this prefix and skip this step.
3. Keep the text before Playwright's action log (the first line starting with `Call log:`).
4. Keep the stable part of Playwright messages, which can change between a test and its retry when the page changes:
   - **Strict mode violations** (`strict mode violation: <locator> resolved to N elements:`): the element count becomes `<n>`, and the enumerated element lines (`    1) <li>…</li> aka locator('li').first()`, and the `...` line ending a long list) are dropped. Their positions (`.first()`, `.nth(1)`, `li:nth-child(13)`) and content shift when the page gains an item.
   - **Locator assertions** (a message with a `Locator:` line): only the lines starting with `Error:` (the matcher line, and `Error: element(s) not found` or a strict mode violation under it), a matcher line after a custom message (`expect(locator).toBeVisible() failed`), `Locator:`, and `Expected…:` / `Received…:` (`Expected:`, `Expected string:`, `Received string:`…) are kept. The timeout, screenshot pixel counts and diff bodies are dropped. Every `Error:` line is kept, not only the first, so that a missing element and several matching elements on the same locator stay apart.
   - Other messages are kept whole, numbered lines included.
5. Replace volatile values with placeholders, in this order:

| # | Matches | Placeholder | Example |
| --- | --- | --- | --- |
| 1 | UUIDs | `<uuid>` | `3f2b8c1e-9a4d-4e5f-8b6a-1c2d3e4f5a6b` |
| 2 | URLs (`scheme://…`, trailing punctuation excluded) | `<url>` | `http://localhost:3000/api?id=4` |
| 3 | E-mail addresses: a local part, `@`, a domain with at least one dot and an alphabetic top-level domain | `<email>` | `qa+1717171717171@test.example.com` |
| 4 | ISO dates and date-times | `<date>` | `2024-03-01`, `2024-03-01T12:34:56.789Z` |
| 5 | Times of day | `<date>` | `09:15:02` |
| 6 | Unix timestamps (10 or 13 digits starting with 1) | `<date>` | `1717171717171` |
| 7 | Absolute paths: POSIX with at least two segments, Windows drive paths | `<path>` | `/home/ci/app/a.json`, `C:\app\a.json` |
| 8 | nanoid-like identifiers: 20+ characters of `A-Z a-z 0-9 _ -` with at least one lowercase letter, one uppercase letter and one digit | `<id>` | `V1StGXR8_Z5jdHi6B-myT` |
| 9 | cuid-like identifiers: 20+ lowercase letters and digits with at least one digit and one letter after `f` | `<id>` | `cjld2cjxh0000qzrmn831i7rn`, `tz4a98xxat96iws9zmbrgj3a` |
| 10 | Durations: a number followed by `ms`, `s`, `sec`, `seconds`, `m`, `min`, `minutes`, `h`, `hours` | `<duration>` | `5000ms`, `2.5 s` |
| 11 | Hex strings of 8+ characters containing at least one letter `a-f` | `<hex>` | `a1b2c3d4e5f6` |
| 12 | Remaining numbers, including inside words | `<n>` | `42`, `0.02`, `h1` → `h<n>` |

6. Collapse whitespace runs to one space and trim.

Why this order: URLs contain slashes and may contain `user@host`, so they are replaced before e-mails and paths; e-mails, paths and identifiers are replaced before durations, hex strings and numbers so each becomes one placeholder; a pure digit run is a number, not hex.

Identifiers are matched as whole tokens, so they are not confused with ordinary text:

- 20 characters minimum and a mix of letters and digits: long words (`internationalization`, `toHaveAccessibleDescription`) and timings (`429ms`) are kept.
- nanoid-like tokens need both cases: `kebab-case` and `snake_case` names keep their words (`checkout-step-2-payment-form` → `checkout-step-<n>-payment-form`). A camelCase name of 20+ characters that contains a digit is replaced, a known trade-off.
- cuid-like tokens need a letter after `f`: pure hex strings, such as a 40-character commit SHA, stay `<hex>`.

Example: `Error: Order sync 3f2b…5a6b rejected by http://localhost:3412/api/orders/77 after 812ms` normalizes to `Error: Order sync <uuid> rejected by <url> after <duration>`, and `User qa.42@example.com cannot open order cjld2cjxh0000qzrmn831i7rn` to `User <email> cannot open order <id>`.

Signatures of Playwright's own messages can change when Playwright rewords them, so compare signatures across runs made with the same Playwright minor version.

## Error categories

Each error (test, step and run error) gets the category of the first matching rule. Rules are ordered; the first match wins. Errors matching no rule go to the uncategorized bucket (`Uncategorized` unless configured), which stays visible so missing rules show up.

Rules from the config (`categories.rules`, see [configuration](../config.md#error-categories)) run **before** the built-in rules (`extend` mode, the default) or **replace** them (`replace` mode). A config rule chooses what it is tested against: the message, the stack, the titles of the failing steps, or all of them.

Built-in rules, tested against the message and the stack:

| Order | Category | Color | Matches |
| --- | --- | --- | --- |
| 1 | Ambiguous locator | violet `#8656b7` | `strict mode violation` (a locator resolving to several elements) |
| 2 | Locator not found | magenta `#ad4681` | `element(s) not found`, `resolved to 0 elements` |
| 3 | Rate limited | teal `#04837c` | `Too Many Requests`, `rate limit` (also `rate-limit`, `ratelimit`), or a 429 in an HTTP context (see below) |
| 4 | Server error | orange `#ab5803` | A 500–599 status in an HTTP context, or followed by its reason phrase: `500 Internal Server Error`, `501 Not Implemented`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`, `505 HTTP Version Not Supported` |
| 5 | Network | cyan `#0a7da1` | `net::ERR_…`, `NS_ERROR_…`, `ECONNREFUSED`, `ECONNRESET`, `ENOTFOUND`, `EAI_AGAIN`, `ETIMEDOUT`, `EHOSTUNREACH`, `ENETUNREACH`, `socket hang up`, `fetch failed` |
| 6 | Assertion | blue `#466cc8` | `expect(`, a line starting with `Expected…:`, `AssertionError` |
| 7 | Timeout | brown `#745f43` | `Test timeout of …ms exceeded`, `Timeout …ms exceeded`, `timed out` |
| — | Uncategorized | neutral `#6b6b6b` | anything else |

An HTTP context is a status code preceded by `status`, `status code`, `statusCode`, `"status":`, `HTTP`, `HTTP/1.1` or `←` (the response line of Playwright's fetch log, shown by a failed `toBeOK()`), with an optional `:` or `=`: `status 429`, `Response status: 503`, `HTTP 500`, `statusCode=502`. A bare number is not enough: `Timeout 429ms exceeded` and `Expected: 200 Received: 500` do not match. `failOnStatusCode: true` throws `500 Internal Server Error`, matched by its reason phrase.

The order matters: a strict mode violation (several elements) is reported apart from a missing one (zero elements) and comes first, since it surfaces through the same actions and expects; a missing element surfaces as a failed `expect` or a timed-out action but "not found" is the useful diagnosis; an HTTP status is the diagnosis even when it surfaces through `expect(response).toBeOK()` or mentions a timeout (`504 Gateway Timeout`), and a response that says "rate limit" is rate limiting whatever its status; `ETIMEDOUT` is a network error; a retrying `expect` reports its timeout but is an assertion failure. An action that times out on an element that does exist (disabled, hidden) is a `Timeout`.

## CategoryDefinition

`{ name, color, builtIn }` — `color` is a `#rrggbb` **reference color** identifying the category in this report: the configured color (a palette name in the config is written as its reference color), the built-in color, or a palette color assigned to a category without one (see [configuration](../config.md#error-categories)). It is a reference, not a rendering instruction: renderers may adapt it per theme (text, background and border shades of the same hue) to meet contrast requirements, and Loupe's renderer does. `builtIn` is `true` for the built-in categories (active in `extend` mode) and for the uncategorized bucket, whatever its name.

## Dimensions

A dimension is an analysis axis computed at run time, so rendering never depends on configuration.

Two kinds of dimensions (see [configuration](../config.md#dimensions)):

- **Automatic** (unless `dimensions.auto` is `false`): every **prefixed tag** `@prefix:value` produces a dimension named `prefix` with `value` (everything after the first `:`), e.g. `@layer:api` → `{ layer: ['api'] }`. Unprefixed tags (`@smoke`) produce no dimension and stay in `tags`.
- **Configured** (`dimensions.definitions`): from a tag prefix, under the configured name (`{ name: 'Layer', from: 'tag', prefix: 'layer' }` → `{ Layer: ['api'] }`), or from an annotation type, the annotation descriptions being the values (`{ type: 'bug', description: 'BUG-1' }` → `{ Bug: ['BUG-1'] }`). A configured tag dimension replaces the automatic dimension of its prefix.

A test can have several values for one dimension. `TestCase.dimensions` only has the dimensions the test has a value for.

## DimensionDefinition

| Field | Type | Description |
| --- | --- | --- |
| `name` | `string` | Key in `TestCase.dimensions`. |
| `source` | `'tag' \| 'annotation'` | Where values come from. |
| `key` | `string` | Tag prefix (without `@` and `:`) or annotation type. Equal to `name` for automatic dimensions. |
| `values` | `string[] \| null` | Expected values declared in the config, `null` when not declared (always `null` for automatic dimensions). Loupe records them without checking test values: consumers compute unknown values (used but not declared) and tests missing a value. |

## Renderer settings

Not part of the data contract. Presentation choices from the [configuration](../config.md#renderer-settings) are written to `index.html` in their own element, next to the report data, and **never to `report.json`**:

```html
<script id="loupe-settings" type="application/json">{"title":"My suite","theme":"system","screenshots":{"defaultView":"side-by-side"}}</script>
<script id="loupe-data" type="application/json">{ …the report… }</script>
```

| Field | Type | Default |
| --- | --- | --- |
| `title` | `string` | `'Loupe report'` |
| `theme` | `'system' \| 'light' \| 'dark'` | `'system'` |
| `screenshots.defaultView` | `'side-by-side' \| 'slider' \| 'overlay' \| 'diff'` | `'side-by-side'` |

The block can gain fields without a schema version change. Renderers fall back to the defaults for missing fields. Type: `RendererSettings`, exported from the package.

## Note

Phase 2 slot. `{ createdAt: date, author: string | null, text: string, testId: string | null }` — `testId` is the test id for a note on a test result, `null` for a run-level note.

## Playwright compatibility

Loupe requires **Playwright 1.52 or later**. 1.52 is the first version providing every reporter API the v1 model relies on; the last one added is `TestResult.annotations` (1.52), needed for per-attempt annotations. The other APIs are older: `TestCase.tags` (1.42), `TestError.location` / `snippet`, `TestStep.location` / `category`.

Newer APIs are used when available, without raising the minimum:

| API | Since | Used for | Before |
| --- | --- | --- | --- |
| `metadata.gitCommit` (`captureGitInfo`) | 1.51 | git commit and branch | CI variables only |
| `TestStep.subtitle` | 1.61 | `Step.subtitle` | `null`; the target is in the title |
| `config.argv` | 1.61 | run scope | `process.argv` |
| `config.filteredProjects` | 1.64 | `project-filter` | command line + projects in the run |

CI runs the test suite on 1.52.0, on the version of the lockfile and on the latest release (`@playwright/test@latest`), so the fallbacks of the table above and the internal `_only` flag are checked on every supported generation.

## How the types and the JSON Schema stay in sync

The JSON Schema is written by hand and **tested against the types** ([`test/schema.test.ts`](../../test/schema.test.ts)). Generating it was ruled out: Loupe builds with TypeScript 7, whose native compiler has no JavaScript API for generators such as `ts-json-schema-generator`.

1. Every object in the schema is closed (`additionalProperties: false`) and requires all its properties, mirroring types that have no optional fields.
2. Sample reports typed with `satisfies LoupeReport` cover every object type, with null and non-null variants. The compiler rejects a sample with a missing or extra field; the schema must accept them. A field added to the types but not the schema (or the reverse) fails one side or the other.
3. Enumerations are runtime constants in `src/schema/v1.ts` and are compared with the schema's enums.
4. Size limits in the schema are compared with the reporter's constants.
5. The report produced by the fixture suite, and the merged sharded report, are validated against the schema.
